# APP DESIGN — oheedet (фаза 2, спецификация)

> Дизайн выведен из [findings.md](../research/findings.md) → раздела «🎯 Продуктовые выводы» (A–H).
> Принцип: самый маленький продукт, который делает дефицит калорий **незаметным и удерживаемым**
> под условия конкретного человека. Всё «на будущее» вынесено в v2+ (см. §3).

---

## 1. Что это и для кого
Приложение генерирует **персональное меню на неделю** (что есть, сколько, когда) так, чтобы
пользователь худел на 0.5–1 кг/нед **без спортзала и без ручного подсчёта калорий** — за счёт
сытной еды (белок/клетчатка/объём) под его аллергии, нелюбимое, бюджет, посуду и режим «на двоих».

**Честная рамка (D-001):** не обещаем чудо-продуктов; единственный механизм — дефицит, а приложение
делает его комфортным.

## 2. Ядро ценности («действующее вещество»)
Из базы: решает не тип диеты, а **приверженность** (T3) + **сытость без подсчёта** (T5/T8/T9) +
**поведенческий автоматизм** (T23–T25). Значит продукт = «готовый режим питания под тебя», а не
диета-спринт и не счётчик калорий.

## 3. Границы MVP (v1) — что входит и что НЕ входит

**Входит (v1):**
1. Короткий профиль → цель по калориям и белку.
2. Генератор меню на неделю (порции + тайминг) под ограничения.
3. Режим «на двоих» (общие ужины).
4. Список покупок + прикидка бюджета.
5. Карточки рецептов, сортировка от простых к сложным.
6. Лёгкий трекинг «съел по плану? ✓/✗ + замена» и еженедельное взвешивание.
7. Guardrails безопасности (кап темпа, скрининг красных флагов → к врачу).

**НЕ входит (v2+, YAGNI — добавим, когда ядро используется и попросишь):**
- Полноценный дневник питания со сканером штрих-кодов (v1 даёт план, а не учёт каждого грамма).
- Гликемическая персонализация по глюкозе/микробиому (T30 — надстройка, не основа).
- Интеграция сна/стресса и связка с проектом pospat (T16/T17 — синергия, но позже).
- Модуль GLP-1, соцфичи, генерация бесконечных рецептов ИИ, аккаунты/облачная синхронизация.

## 4. Пользовательский поток
1. **Онбординг-профиль** (коротко, не занудный опрос):
   пол, возраст, рост, вес, цель по весу, уровень бытовой активности; аллергии (мультивыбор),
   нелюбимое (теги), бюджет (низкий/средний), посуда/техника (чекбоксы: плита, духовка,
   микроволновка, блендер, мультиварка…), тумблер «готовим на двоих» (+второй мини-профиль).
2. **Расчёт целей:** TDEE (Mifflin-St Jeor) − дефицит → дневные калории и белок; клетчатка ≥30 г.
3. **Генерация недели:** движок собирает 7 дней приёмов под цели и ограничения.
4. **Выдача:** экран недели (приёмы, порции, время) → список покупок с бюджетом → карточки рецептов.
5. **Ежедневно:** отметка «съел по плану / заменил», раз в неделю — вес → петля обратной связи.

## 5. Компоненты (каждый — одна ответственность)

### 5.1 Профиль и цели (`targets`)
- Вход: профиль. Выход: `{kcal_target, protein_g_target, fiber_g_target=30, tempo}`.
- TDEE = Mifflin-St Jeor × коэффициент активности; дефицит 500–600 ккал/д; темп кап 1 кг/нед (T32).
- Белок 1.2–1.6 г/кг (по текущему весу, при ожирении — по скорректированному) (T5).
- `ponytail: одна формула (Mifflin-St Jeor); не добавлять Katch-McArdle и пр., пока не понадобится.`

### 5.2 База рецептов (`recipes.json`)
- Курируемый набор (старт ~60–100 рецептов), каждый с полями:
  `{id, name, meal_type, kcal, protein_g, fiber_g, energy_density, cost_tier, cookware[],
    allergens[], cuisine, difficulty(1–3), time_min, ingredients[], steps[]}`.
- Макросы на порцию **посчитаны при авторинге** — v1 не требует живой базы нутриентов.
- `ponytail: рецепты несут готовые макросы; таблицу состава продуктов (USDA/аналог) подключаем
  только когда разрешим свап ингредиентов пользователем — не раньше.`

### 5.3 Генератор плана (`planner`)
- Вход: цели + ограничения + база рецептов. Выход: 7×приёмы с порциями и временем.
- Логика (жадная): фильтр по аллергенам/нелюбимому/посуде/бюджету → на каждый день набрать приёмы
  под калораж (±10%) и белок (≥цель), копить клетчатку до ≥30 г, предпочитать низкую энергоплотность
  (T9), больший калораж — на первую половину дня, лёгкий ранний ужин (T14).
- Порции масштабируются, чтобы попасть в дневную цель.
- `ponytail: жадный перебор по дням; менять на оптимизатор (ILP) только если жадность стабильно не
  добивает цели по калориям/белку.`

### 5.4 Режим «на двоих» (`couple`)
- Общий ужин: один рецепт, порции масштабируются под цель каждого; завтрак/обед — по желанию общий
  или раздельный. Один общий список покупок.
- `ponytail: делим только ужин по умолчанию; полный «двойной планировщик» — если попросят.`

### 5.5 Список покупок и бюджет (`grocery`)
- Агрегирует ингредиенты за неделю, группирует по категориям, суммирует прикидку стоимости из
  `cost_tier` ингредиентов. Цель — «принципы из дешёвых продуктов» (T40), без экзотики.

### 5.6 Guardrails безопасности (`safety`)
- Кап темпа ≤1 кг/нед, минимум калорий не ниже безопасного (не VLCD) (T32).
- Онбординг-скрининг: диагнозы/лекарства (щитовидка, СПКЯ, психотропные) и мини-скрин РПП (тип
  SCOFF); при флагах — не жёсткий дефицит, экран «к врачу/специалисту» (T34, T36).
- Меню закрывает микронутриенты за счёт овощей/бобовых/круп (T33).

## 6. Данные
- v1: `recipes.json` (курируемый, версионируется в git). Никакой внешней БД/бэкенда не нужно.
- Профиль и прогресс — локально на устройстве.

## 7. Технологии и платформа — **решение по умолчанию (флаг)**
- **Веб-приложение (PWA), работает в браузере телефона; без бэкенда, без аккаунтов.** Рецепты —
  бандл JSON, план считается на клиенте, профиль/прогресс в localStorage. Пара — второй профиль в
  том же приложении (одно домохозяйство).
- Почему так (ponytail): максимум ежедневной пользы при минимуме инфраструктуры — нет сервера,
  магазина приложений, регистрации. Стек простой (статический фронтенд).
- **Переиграть, если хочешь:** Telegram-бот (ещё ниже порог, но слабее UI меню) или нативное
  мобильное (дороже, нужен магазин, синхронизация). Кросс-девайс синхронизация/аккаунты — только
  когда реально понадобится.

## 8. Решения по умолчанию (принял без ожидания; скажи, если иначе)
- Платформа: **PWA/веб без бэкенда** (§7).
- Учёт калорий вручную: **нет** — v1 даёт план + лёгкую отметку «съел/заменил», полный дневник → v2.
- Ввод «доступных продуктов»: **не спрашиваем поштучно**; исходим из бюджет-режима + локальных
  типовых продуктов, свап ингредиента — в карточке рецепта. (Убирает занудный опрос из requirements.)
- Старт рецептов: ~60–100 курируемых (хватит на разнообразную неделю), расширяем по мере надобности.

## 9. Открытые форки (нужно твоё слово только если не согласен с §8)
- Платформа (веб vs Telegram vs нативное).
- Кухня/культура рецептов на старте (условно «универсальная/славянская/средиземноморская»?).
- Нужен ли многоязычный/многопользовательский режим сразу или только «под себя + жена».
